# 从"任务状态"到"会话路线图" · 设计论纲

> 2026-11-17 · 讨论产物，非实现计划。决定之前先看这张地皮图。

## 0. 谁已经占着什么

| 现有物 | 它给的是 | 它给不了 |
|---|---|---|
| DSH **轨迹** | 记录的原子与时间：每次调用、token、时长、输入输出 | 这些记录"为了什么"、哪些路没走 |
| **dsh-context** | 上下文成本、文件活动、命令执行、agent 拓扑 | 语义、意图、因果 |
| **better-sidebar** | 文件树、Git、子代理、侧聊 | 会话内的叙事 |
| **bearings** | 跨线/跨会话方位："上次之后变了什么"、意图台账 | 会话内的一次任务怎么长出来 |
| **git** | 字节层面的变化与其历史 | 为什么、放弃了什么 |
| **我们 v0.2** | 用途归并 + 计划双源 | （正在被轨迹和 context 挤到同质） |

结论：**"记录了发生什么"这一层已经被占满**。我们继续做展示只会更精细地重复别人。

## 1. 你的判断我同意一半

- **保留**：`进行中/空闲 + 上一步 N 秒前结束`。它是"现在"的锚点，一条信息、零成本、没有替代品。
- **撤掉**：`拆成了几步 / 最近做了什么 / 动过的文件`。它们回答的是"发生了什么"，这是轨迹和 context 的本职；我们做只是把别人的数据换个排版。

## 2. 变化的可操作定义

> 变化 = 可能性空间的一次收缩。在 t 时刻有若干条可行下一步，其中一条被执行，其余被关闭。

于是"变化"有三个可观测维度：

| 维度 | 例子 | 谁有 |
|---|---|---|
| **act** 做了什么 | 写了 `monitor.js`，跑了测试 | git / 轨迹 / 我们 |
| **option** 曾可以做什么 | 本来可以换方案 A，但选了 B | **没人有** |
| **reason** 为什么是这个 | 因为 B 的改动面小 | **没人有**（除了人脑） |

只记录 act 的东西永远只是日志；**拉开可能性平面**靠的是 option 与 reason。这正是你说的"越多的高相关维度越能拟似真实的变化"。

## 3. roadmap 的三层结构

```
L0 里程碑（确定性，零模型）
   可验证的落点：文件落盘 / 测试转绿 / 依赖装上 / 一段代码被删掉
   一个里程碑 = 一个可回指的事件集合

L1 岔路（半确定性）
   决策点：选了 A，同时关掉了 B、C
   来源①  模型声明（todo 改向、checkpoint 里的"改主意"）
   来源②  启发式（同一处连续失败 2 次后换招 = 一条路被放弃）

L2 意图（模型，稀缺）
   声明意图 vs 实际落点 → 漂移量
   只有在这一层才花模型预算，且只在章边界
```

每条边挂 **evidence**（seq / 调用 / 文件 diff）。没有证据的断言不上图——这是 `codicel` 的教训：**每个断言都能回指证据，否则就是讲故事**。

## 4. 时机：为什么必须"里程碑触发"

你担心的平衡问题，用一条规则就能解：

- **太早** = 没有证据的预测。所以我们**从不预测下一步**，只记录已经闭合的东西。
- **太晚** = 复盘。所以里程碑一闭合就写入（测试转绿是瞬时的，不是等会话结束）。
- **L2 只在章边界**：每 N 个里程碑、或出现岔路时，才允许一次模型生成。预算可数、可上限。

一句话：**确定性层跟着事件实时长，语义层跟着章节批量长。**

## 5. 含金量在哪（直说）

一个专业的项目管理 skill，或者干脆让模型现读日志，都能做出同样漂亮的路线图。所以含金量不在"分析能力"。在三件别人拿不到的东西：

1. **底料**：一个常驻的、每会话的**变更索引**（里程碑/岔路/证据链），随时是最新的、且免费维护。skill 是"被叫醒才算一次"；我们是"一直在算"。
2. **时机**：知道什么时候值得花一次模型调用、什么时候不值得。这是产品判断，不是提示词能替代的。
3. **可审计**：每个断言标注来源（声明 / 观测 / 推断）并可回指事件。混在一起就是新的黑话。

所以：**PM skill 是我们的消费者，不是竞争者。** 我们把它的输入准备好，它就可以秒答。

## 6. 面向模型的工具：不是"另一个摘要"，是"问历史"

你说"从人们没想到的角度展示变化"——我以为角度就是：**让模型消费自己的历史**。

`tell_the_diff` 从"写"扩展成"读写两用"：

| 模式 | 问/答 | 价值 |
|---|---|---|
| **write** | "我在岔路 X 选了 A，因为 B" | 人看到的路线图有"为什么" |
| **read** | "这轮之前我们试过什么、放弃了什么、现在被什么约束" | 模型下一步不再重复踩坑 |
| **read** | "文件 f 在本会话里变过几次、每次为什么" | 改动前的自检 |

第三行是 git 给不了的：git 有行级历史，没有"每次为什么"。

## 7. 调研：确实有领域，而且不止一个

不是新发明，是**把成熟构件第一次装进"人与 agent 的会话"里**：

- **process mining / task mining** —— 事件日志 → 过程模型（α 算法、workflow net）。其中 *translucent event log* 记的不只是"执行了什么"，还有"当时哪些活动是 enabled"——**这就是"被放弃的路"的正式版本**。[过程挖掘](https://theses.hal.science/tel-01010756/document) · [translucent activity relationships](https://rd.springer.com/chapter/10.1007/978-3-031-70396-6_9)
- **goal / plan recognition** —— 从观测反推目标（Ramírez & Geffner 用规划器做识别，不需要计划库）。我们的"按动作推断步骤"就是它的弱化版。[Plan recognition 综述](https://www.sciencedirect.com/topics/computer-science/plan-recognition)
- **provenance：why 与 why-not** —— 解释"为什么发生"以及"为什么没发生"（negative provenance / why-not queries）。我们的"岔路"在数据库语言里叫 why-not。[Negative provenance](https://dl.acm.org/doi/abs/10.1145/2535771.2535799) · [PUG: why/why-not provenance](https://dlnext.acm.org/doi/10.1007/s00778-018-0518-5) · [Provenance summaries](http://www.vldb.org/pvldb/vol11/p1954-lee.pdf)
- **design rationale / IBIS** —— 把决策与理由结构化留存，专门解决"半年后没人记得为什么"。
- **history flow** —— Viégas 等用"流"可视化文档在版本间的演化，正是"随时间变化的形态"。[History Flow (CHI 2004)](https://dl.acm.org/doi/epdf/10.1145/985692.985765)
- **sensemaking / information foraging** —— 人在信息空间里怎么找、怎么形成解释（Pirolli & Card）。[Information foraging](https://www.sciencedirect.com/topics/computer-science/information-foraging)
- **软件考古** —— `codicel`：读完整 commit 历史，讲"变成了什么、为什么、什么被留下"，每个断言锚到 commit。[codicel](https://github.com/sirmos/codicel)

缺的那块很清楚：**上面每一件都假设"人做事、系统记录"；没有一件假设"agent 做事、人要看懂"。**

## 8. v0.3 范围提案（小而可验，不新增模型调用）

1. **L0 里程碑**：确定性抽取（新建/修改文件落点、测试/构建结果翻转、依赖变更、子代理返回）。UI 先做纵向时间线，不画图。
2. **L1 岔路（启发式版）**：同一目标连续失败 ≥2 次 → 生成一条"放弃：<方法>"。不做模型推断。
3. **保留**：状态 + 上一步时间 + 人话摘要（`tell_the_diff` 的 write 通道）。
4. **撤掉**：文件列表、命令流水（交给轨迹与 context）。
5. **验判断**：用户能否在 5 秒内说出"现在在哪个里程碑、上一个是什么、有没有岔路"。

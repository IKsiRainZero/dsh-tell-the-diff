# 这一路

模型埋头执行时，用户只看到滚动的工具调用和思考链。这张卡回答一个问题：**这一路是怎么走到现在的？**

## 它解决什么

用户为了对齐现状，通常要在主对话里再问几轮："做到哪了？""刚才那个报错是问题吗？""为什么换方案了？"每一轮都花人的注意力，也花模型的 token。这张卡把这些信息搬到输入框下面和右栏，且默认不花任何模型调用。

它不替代对话，也不和对话抢位置：默认沉默，只有卡片本身在更新。

## 卡上有什么

| 区块 | 内容 | 来源 |
|---|---|---|
| 现状一行 | `空闲 · 上一步 12 秒前结束` / 最近落点 | 会话事件流 |
| 人话摘要 | 模型写的一句话 | `tell_the_diff` 工具 |
| 落点 | 验证通过/失败、新建文件、改动代码、子代理交回、提交 | 会话事件流 |
| 岔路 | `卡住了` / `换过路` | 会话事件流（启发式） |
| 计划 | 模型声明的步骤，或按动作推断，**标注来源** | `todo_write` / `tell_the_diff` / 推断 |
| 需要你决定 | 模型攒下的问题 | 同上 |
| 可能的风险 | 用户该提前知道的事 | 同上 |
| 还没解决的问题 | 失败的、还没被后续成功覆盖的动作 | 会话事件流 |
| 角落一行 | 文件数、动作数、出错数 | 派生 |

## 为什么是"落点"而不是"活动流水"

`read → read → grep → edit` 是准确的，但对读者没有意义：它说的是"跑了什么"，没说是"为了什么"，也没说这些动作之后**世界有什么不同**。

落点只记"工作状态确实改变"的瞬间。两个落点之间的动作属于执行细节，属于 DSH 的轨迹视图，不属于这张卡。

## 为什么会有"岔路"

变化不只是"做了什么"，还是"哪些路被关掉了"。同一个目标连续失败两次，通常意味着换了一条路——但这是一个**推断**，所以它带着状态说话：

- `卡住了` —— 失败还在继续，只能说明现在卡在哪儿；
- `换过路` —— 之后确实换了做法，才敢说那条路被放弃了。

## 隐私

全部数据留在本机进程内存和会话日志里，没有一个字节发到外部服务。轮询只打到 `127.0.0.1` 上的 DSH 自身。


## 为什么它不会变成第二个 token 黑洞

1. **默认零模型调用。** 卡片的全部内容是会话日志的改写，不新增请求。
2. **工具描述有界。** `tell_the_diff` 的参数模式是固定的几十个 token，不随会话增长。
3. **不存全量 transcript。** 每会话最多 20 条活动、10 条问题、5 次检查点、40 个文件；空闲 30 分钟后整份状态被回收。
4. **一次轮询一个 GET。** 1.5 秒一次，只回当前会话的派生视图，不回日志。

## 它不做什么

- 不打断任务：没有弹窗、没有 steering、没有自动审批、不替你发消息。
- 不复制别的插件：文件树、Git、子代理拓扑属于 `dsh-better-sidebar`；跨会话方位属于 `bearings`。
- 不做「另一个聊天侧栏」：主视图是状态卡，不是对话流。
- 不评价模型：卡上只描述发生了什么，不打分。

## 读卡的一点经验

- 卡上写着「正在运行命令」超过一两分钟，通常是在跑测试或构建，不必打断。
- 「还没解决的问题」出现两条以上，才是值得看一眼的信号。
- 摘要区是模型自己写的；它偷懒写得含糊时，卡会退化成纯事件流——这本身也是信息。
